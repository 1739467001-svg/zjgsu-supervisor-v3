## 二、需求一：学期档案与统计仪表盘

### 2.1 学期查看与数据留存

- 在业务页面统一提供“查看学期”下拉框，使用 `2025-2026-2`、`2026-2027-1` 等明确标签。
- 切换查看学期只改变当前用户的查询范围，不改变全校正在使用的当前学期。
- 课程列表、评价列表、听课计划、学院工作台、统计及批量导出统一使用所选学期。
- 历史课程、评价、评分和计划持续留存；保留原课程、教师、学院与评价的关联。
- 历史学期默认只读。纠错若确有需要，另行设计受控流程，不开放普通用户直接修改历史记录。
- 新学期建立独立课程与评价记录，初始评价数为零；不通过删除旧评价实现“清零”。

### 2.2 统计口径

- 学院来自所选学期实际课程和评价关联数据，不生成虚构学院，不静默合并或丢弃真实学院。
- 评价次数统一统计“已提交评价”；草稿继续保留在列表中，并明确不计入统计。
- 课程覆盖率为“至少有一条已提交评价的课程数 ÷ 所选范围课程总数”；同一课程多次评价不重复计入覆盖课程数。
- 平均评分仅按实际有效评分计算，明确计分条数；没有评分显示“暂无评分”，不是零分。
- 三张图使用相同学院集合、排序、学期和权限范围；学院名称完整可读。
- 如存在缺失学院、断开关联或异常评分，单独提示核查，不自动编造、归类或修复生产数据。

### 2.3 精简展示

保留三个关键图表：课程评价覆盖率、各学院评价次数、各学院平均评分；保留课程总数、评价次数、整体覆盖率和平均评分摘要及学院明细表。

删除重复的学院分布饼图、非关键的星期分布图等展示，保留其底层历史记录。以真实学院数量为准，不再沿用早期“固定 8 项、其余合并”的验收标准。

### 2.4 验收

1. 同一账号切换新旧学期，课程、评价、计划、统计与导出一致变化。
2. 历史评价详情中的课程、教师、学院、评分与评语完整可查。
3. 三图学院集合一致，学院评价次数之和等于同范围已提交评价总数。
4. 新学期无评价时，显示零次数、暂无评分，不混入旧学期数据。
5. 历史写入操作在页面和服务端均被限制，不能仅靠隐藏按钮。

## 三、需求二：多角色切换与授权

### 3.1 身份与范围

截图明确的业务角色如下。表中“可评”指提交听课评价，不意味着能修改他人评价。

| 业务角色 | 截图要求 | 拟定范围与边界 |
| --- | --- | --- |
| 研究生院管理员 | 可评、可查 | 全校范围；具体管理动作逐项授权 |
| 院级管理员 | 可评、可查 | 本学院范围；跨学院职责须明确配置 |
| 教学秘书 | 可查 | 默认本学院；不得提交评价，除非另有督导角色 |
| 校级督导专家 | 可评 | 可评价全校课程；默认查本人评价，不因“校级”自动获得他人评语权限 |
| 院级督导专家 | 可评 | 可评价授权学院课程；默认查本人评价 |

历史查询同样受权限限制。“各角色需保留历年数据可查”不等于所有角色可查看全校所有人的评价。

### 3.2 交互与实现原则

- 一个账号可绑定多个经授权的角色，不创建多套重复账号。
- 顶部显示当前身份及学院范围，提供“切换身份”入口；切换后菜单和工作台随之变化。
- 明确区分角色权限、学院范围和所选学期三个维度。
- 服务端验证当前身份属于本人、目标数据在范围内；接口直调、导出、打印同样校验。
- 建议使用明确的当前身份模式，不把所有附加角色权限无提示叠加；最终采用前需检查与现有实现的兼容性。
- 保留必要的授权变更记录，避免普通用户自行增加角色或扩展学院范围。

截图指定了三名人员及所有院级管理员的双身份需求。人员姓名、账号和具体双角色组合通过单独的授权名单确认，不在仓库中公开名单，不能仅按姓名自动授权。

### 3.3 验收

- 五类角色分别验证菜单、课程范围、评价创建、本人评价详情、他人评价访问、计划操作、导出和打印。
- 双身份账号切换前后功能符合当前身份，学期选择不意外改变。
- 教学秘书无督导角色时不能评分；院级角色不能访问未授权学院数据。
- 督导能打开本人评价、操作当前学期本人计划；不能凭评价 ID 查看无权访问的他人评语。
- 历史只读限制对所有身份一致生效。

## 四、需求三：总课表与 MBA 两个上传入口

### 4.1 页面流程

在“上传课程数据”下设置两个明确入口：

1. 全校研究生总课表（不含 MBA）。
2. MBA 课表。

两者复用现有 `scripts/import-courses.ts` 所依赖的解析能力，核实其模块结构后接入网页，不另写一套不一致的解析规则，不用手写 SQL 导入。

统一流程：选择目标当前学期 → 上传文件 → 解析预览 → 显示异常与数量 → 确认导入 → 显示结果。

### 4.2 数据保护

- 分别支持已验证的两种 Excel 布局；格式或学期不匹配时明确拒绝，不猜测导入。
- 预览显示文件类型、目标学期、解析数量、合并数量、学院分布、预计新增和更新数量。
- 两份文件分开上传时，不删除另一份课表的课程；重复上传不重复新增。
- MBA学院与工商管理学院保持独立，沿用已验证的拆分规则。
- 不改写历史学期课程，不破坏已有评价与课程关联。
- 对已有评价课程的名称、教师或学院变动，先识别影响并提示，不能静默改变历史含义。
- 导入前备份，错误时停止并保留可定位的错误信息；不记录密钥或完整敏感配置。

### 4.3 验收

- 用指定两份 2026 秋原始 Excel 复验，核对已确认基准：合计 1832 门、24 个学院；MBA学院 354 门、工商管理学院 88 门。
- 上述数量仅作为这两份原文件的验收基准，不硬编码到系统，也不套用到以后学期。
- 测试先总课表后 MBA、先 MBA 后总课表、重复上传、错误格式、错误学期、带已有评价课程的更新。
- 所有导入测试先在隔离测试环境进行，生产环境不为验收重复导入课表。

## 六、需求五：上线开放与数字办迁移

“国庆后开放督导使用”作为业务目标日期，须以关键验收通过为前提。

### 6.1 当前服务器上线

- 先恢复服务器连接并确认健康状态；检查候选检查进程是否仍运行。
- 在本地或构建环境完成高负载检查，避免在生产小内存服务器重复运行。
- 留存版本号、数据库和附件备份、旧构建产物及回滚办法。
- 先完成 7a44b18 的学期与统计验收，再部署后续角色、上传功能，便于定位问题。
- 未验证前不宣布“全部功能一致”或“部署完成”。

### 6.2 数字办迁移

需要数字办确认目标服务器、网络访问、域名与 DNS 权限、HTTPS 证书、备份位置和维护窗口。

建议流程：部署目标环境 → 恢复完整数据与附件 → 验证账号和权限 → 核对各学期课程/评价/计划数量 → 在约定写入暂停窗口进行最终同步 → 切换域名 → 验证 → 保留旧环境供回退。

避免新旧服务器同时接受评价写入。回退前先核查切换后产生的新数据，不能简单切回旧库导致丢失。

已暴露密钥的轮换作为独立安全变更安排，按已有手册执行并通知用户重新登录；不与未验证的功能改动混为一次操作。独立安排不代表可以长期延后：应在恢复访问后优先评估，并在扩大开放前完成；若仍有已暴露的有效会话签名密钥，不应直接扩大开放。

| 阶段 | 工作 | 完成标准 |
| --- | --- | --- |
| P0：恢复与保护 | 恢复连接、确认服务健康、核对备份和历史数据 | 可访问、可诊断、具备可执行回滚方案 |

## 八、实施前仅需确认的业务事项

1. 管理员“可查”是否包含权限范围内全部评语及评分，是否有匿名展示要求。
2. 教学秘书是否可导出明细和打印完整评价，还是仅可查看统计与进度。
3. 双身份人员的准确账号、角色组合、学院范围；所有院级管理员的对应名单。
4. 历史记录按现行授权学院还是评价发生时的学院授权查看；建议默认现行明确授权，特殊情况单独配置。
5. 数字办迁移负责人、目标环境、域名及可接受维护窗口。

上述待确认项只影响对应模块，不妨碍先完成已明确的学期留存与统一统计上线。

## 九、进一步明确业务边界

以下为拟采用的规则；标注“待确认”的内容不得直接转换为线上授权。

### 9.1 “查看学期”与“启用新学期”是两个操作

| 操作 | 使用者 | 影响 | 保护措施 |
| --- | --- | --- | --- |
| 查看学期 | 已登录且具备相应业务权限的用户 | 只影响本人页面、查询和导出 | 展示所选学期，不改变全校当前学期 |
| 启用新学期 | 经明确授权的管理人员 | 全校后续业务写入目标发生变化 | 明确确认、备份、检查课表和未完成业务，记录操作 |
| 导入课表 | 具备课表导入权限的管理人员 | 更新确认范围内的课程 | 先预览，再确认；不得凭管理员名称自动赋予所有管理权限 |

- 顶部同时区分“系统当前学期”与“正在查看的历史学期”，避免老师误以为全校学期被切换。
- 开着评价表时切换学期或身份，先处理未保存内容；不能直接丢弃输入。
- 若管理员在老师填表期间启用新学期，提交时再次核验，明确提示原学期已归档；不得将旧课程评价自动写入新学期。
- 启用前提示旧学期未提交草稿和未完成计划数量。旧草稿保留，不自动转为已提交，也不自动转移学期。
- 历史详情页显示记录自身的真实学期；不能仅显示全局筛选学期，造成记录归属误解。
- 历史只读、未保存提示和启用前检查是目标验收要求，其中新增交互须检查现有代码是否已覆盖，不能视为 7a44b18 全部已实现。

### 9.2 多角色的可执行约束

- 业务名称与程序角色值必须先建立映射，尤其“院级管理员”不能未经检查直接映射为全校系统管理员。
- 系统技术管理员与研究生院业务管理员分开描述；拥有用户管理权限不自动意味着可阅读所有评语。
- 推荐给需要评价的管理员配置相应督导身份；其账号同时可评、可查，通过切换入口使用。是否允许管理身份下直接评分，作为交互选择待研究生院确认。
- 普通督导默认只看本人评价；管理员和秘书能否阅读完整评语及导出明细，按第八节确认结果实施。
- 未确认的新授权不发放；现有权限只记录并评估，不在本次文档阶段批量修改账号。
- 若授权被撤销，后续请求必须失效，不能依赖旧页面或旧会话继续访问。角色切换后清理不再授权的页面数据。
- 测试多浏览器标签页的身份切换，防止一个标签页悄悄改变另一个标签页的提交身份。

### 9.3 统计数字必须能解释

- 整体平均分按各条有效评价计算，不能直接平均各学院平均分；学院人数和计分条数不同会造成误差。
- 展示平均分所用的具体字段、评分量表和有效值规则；沿用现有业务定义，不临时创造综合分算法。
- 无课程时覆盖率显示“暂无课程”，避免除零；有课程但无已提交评价时显示 0%。
- 一门课程被多个督导评价：次数累计多条，已覆盖课程只计一门。
- 数据加载失败显示错误与重试，不能伪装成“0 条评价”。
- 统计页说明“草稿不计入”，列表显示状态，避免总列表比统计多时被误认为丢失数据。
- 历史学院按该学期真实归属显示。学院后来合并或更名，不自动重写历史；跨年合并报表不纳入本期，另行确认映射。
- 页面与导出标注学期、范围、生成时间；截图核验应使用同一数据时点，允许真实新增评价导致后续数字变化。

## 十、课表导入的异常处理规则

本节描述目标行为，须先核对现有导入工具的匹配与事务机制，再确定具体改造。不得为了实现规则直接新增生产表或修改生产数据。

| 情况 | 拟采用行为 | 不允许的处理 |
| --- | --- | --- |
| 同学期、同类型、同一文件重复上传 | 识别为重复或无变化，返回明确结果 | 再新增一套相同课程 |
| 两个入口先后上传 | 各自处理对应来源，并保留另一来源 | 用当前文件全量覆盖整个学期 |
| 新课表没有出现之前的某门课 | 保留并提示差异；停开课另行确认 | 自动删除课程及关联评价 |
| 有稳定课程标识，且记录未被评价 | 按已验证匹配规则展示预计变更 | 只按课程名称相同就合并 |
| 课程已有评价，关键字段改变 | 阻止静默覆盖并给出冲突清单 | 将原评语关联到另一教师或学院 |
| 无法确定两条课程是否同一门 | 标记冲突，要求确认或修正源文件 | 按相似名称猜测合并 |
| 文件学期与目标不符 | 拒绝正式导入，说明冲突 | 自动改学期继续导入 |
| 文件没有可可靠读取的学期字段 | 要求明确确认目标学期和格式来源 | 宣称已自动验证文件学期 |
| 预览后文件、目标学期或相关数据变化 | 旧预览失效，重新预览 | 将过期预览直接应用 |
| 网络中断、重复点击确认 | 查询批次结果，防止重复执行 | 直接反复导入尝试 |
| 执行失败 | 明确完整失败或实际已完成范围；优先设计可原子回滚的写入 | 在部分成功时显示全部成功 |

预览建议显示：原始行数、有效课程数、合并结果、新增、变更、无变化、冲突和错误。各指标注明含义，不强行让“原始行数”等于“最终课程数”。

导入结果建议记录批次、操作者、目标学期、文件类型、文件指纹、结果数量与时间。优先利用现有记录能力；若确需新增结构，单独评审迁移与回滚。上传文件仅授权人员可取用，不通过公开链接暴露。

## 十二、发布准入与问题处理

### 12.1 必须阻止发布的问题

- 历史记录丢失、串学期、课程与评价关联错误。
- 未授权用户能读取评语、导出明细或写入他院数据。
- 督导打不开本人评价，或不能正常保存/提交当前学期评价。
- 课表重复、跨来源覆盖，或导入结果不可核实。
- 服务器健康状态不明、备份不可用，或没有可执行的回退办法。

图表间距等轻微问题可登记后安排修复，但不得将学院名称截断、错误数字、手机无法评分等影响理解或主流程的问题当作纯美观问题放行。

### 12.2 发布与回滚边界

- 各阶段单独确定提交号和验收范围，不把所有改动合成一个无法定位的大版本。
- 纯代码回退仍需核查新版本上线后是否产生数据变化；尤其新增写入格式时，不能默认旧版本可直接读取。
- 回滚前确认新增真实评价已保留；数据库恢复不得覆盖上线后老师的新记录。
- 如果涉及结构迁移、批量授权、数据纠错或密钥变更，先列出具体影响和独立回滚方案，取得对应授权。
- 生产验收以只读检查为主；需要写入验证的场景优先在隔离环境完成。不得伪造老师评价来填充统计图。

### 12.3 下一步执行包

1. 恢复生产访问，核查健康状态和备份；当前方案不代表已恢复。
2. 完成已提交学期功能的 A01—A05、E01 验收；需要写入的部分先在隔离环境验证。
3. 核查现有五角色映射，形成“现状—目标—差异”表，提交双身份名单确认。
4. 复核现有导入器的课程匹配规则与失败行为，确定双入口改动范围。
5. 分阶段开发、测试和上线，最后按稳定页面制作用户手册。

本方案不承诺未经评估的工期，也不把待确认规则、待开发交互或未完成验收写成已交付功能。
