v3 与 v2 共享 commit 祖先，线上若出急修，可直接 `cherry-pick` 同步：

```bash
git remote add v2 https://github.com/1739467001-svg/zjgsu-supervisor-v2.git
git fetch v2 && git cherry-pick <commit>
```

**方向只能是 v2 → v3。** 3.0 未验收前，一行代码都不推向生产。

## 二、开发约束

1. 只在 v3 开发，v2 保持线上现状
2. 以稳定运行 5 个月的版本为基准，每处改动需说明对现有运行的影响
3. v2 全部功能只增不减
4. 业务流程与逻辑不变，不重构流程、不改角色划分、不改评价表结构
5. 只修必要 Bug：会导致数据错误、丢失、越权的才修
6. **老师侧操作只能更简单，不能更复杂**（硬约束）

## 四、角色体系设计（方案 A）

通讯录 101 行 / 100 个唯一工号：

| 拟分配角色 | 人数 | 系统现状 |
|---|---|---|
| 学院教学秘书 | 44 | 已有 `college_secretary` |
| 学院分管领导 | 25 | **需新增** |
| 院级督导专家 | 17 | **需新增** |
| 校级督导专家 | 9 | 已有 `supervisor_expert`，需区分校级/院级 |
| 研究生院主管 | 6 | 已有 `graduate_admin` |

权限边界（据学校文档）：**校级督导可查看和评价全校课程，院级督导仅限本学院。**

**方案 A**：底层按「一人可有多个身份」存储，界面上只有真正拥有第二身份的人才出现切换入口。通讯录中实际具备双角色的仅 1 人（傅培华：研究生院主管 + 校级督导专家），而「学院分管领导」角色定义本身即「同时负责听课和管理」，属于一个角色两种能力，无需切换。

> 99 人界面零变化，符合「老师操作不能更复杂」的约束；后续给任何人增加身份都是配置操作，无需改代码。

**⚠️ 已知数据问题**：通讯录中 34 人的学院名与标准表不一致，其中以下 11 人现有模糊匹配也兜不住，导入后将看不到任何课程——

| 通讯录写法 | 标准表 | 人数 |
|---|---|---|
| 人文学院 | 人文与传播学院 | 5 |
| 国际教育学院 | 标准表中无 | 3 |
| 未来传播学院 | 标准表中无 | 2 |
| 法律硕士教育中心 | 标准表中无 | 1 |

需以秋季课表的「开课院系」为准建立归一映射。
